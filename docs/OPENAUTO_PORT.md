# Android Auto projection architecture

NavOnWeb implements the Android Auto projection path as Android-native Kotlin components. Selected OpenAuto interfaces are retained under `third_party/openauto-reference/` for attribution and comparison, but the Qt desktop application is not used at runtime.

## Data flow

```text
Android Auto Developer Head Unit Server
  -> AASDK framing and TLS
  -> service and media channels
  -> MediaCodec video decoder
  -> WebRTC video source and local preview
  -> paired browser
```

Touch input follows the reverse path from the browser through viewport mapping to the Android Auto input channel. Audio and microphone samples use bounded PCM pipelines alongside the video session.

## Main components

| Function | NavOnWeb implementation |
|---|---|
| Session bootstrap | `AasdkProjectionRuntime` and classes under `openauto/protocol/` |
| Video decode | `MediaCodecVideoSink` |
| Browser video | `WebRtcProjectionController` and `WebRtcTextureVideoBridge` |
| Touch input | `TouchMapper`, `OpenAutoInputSink`, and the AASDK input channel |
| Audio | `OpenAutoPcmSink` and the browser PCM pipeline |
| Microphone | Browser microphone framing and the AASDK microphone channel |
| Night mode | `NightModeResolver` and the sensor channel |
| Foreground lifecycle | `ProjectionService` |

## Connection and session lifecycle

The current endpoint mode connects to Android Auto's same-phone Developer Head Unit Server at loopback port `5277`. The protocol implementation performs version negotiation, TLS, authentication completion, service discovery, channel opening, media setup, and ping/pong handling.

Recoverable connection, read, and ping failures close the old transport before retrying from version negotiation with bounded backoff. Protocol-version, TLS-policy, credential, and explicit peer-shutdown failures end the session instead of retrying indefinitely.

Android Auto identity material is supplied outside the source tree. It is not generated by the application and is not included in this repository.

## Video and browser output

Android Auto H.264 access units are decoded to a Surface. A shared EGL texture can feed both the local preview and the WebRTC sender without a bitmap copy. The browser codec preference supports `AUTO`, H.264, VP8, VP9, and AV1; availability depends on Android encoder and browser decoder capabilities.

`AUTO` prefers a usable hardware codec. Explicit VP9 or AV1 selection may use software encoding and can consume substantially more power. If the WebRTC path cannot start, an authenticated low-rate JPEG path remains available as a compatibility fallback.

The embedded HTTP server publishes the browser application and authenticated signaling endpoints. Pairing and authorization are decided by the phone. A configured public relay can forward browser messages, but it does not replace the phone's authorization decision.

## Touch, audio, and microphone

Browser pointer coordinates are normalized against the visible Android Auto content rectangle. Letterbox and pillarbox areas do not generate Android Auto touches. Input is sent only after the input channel is bound, and pending gestures are cancelled when the viewport changes.

Android Auto media, guidance, and system PCM streams are converted according to the active access tier and forwarded through bounded queues. Slow browser consumers cannot block the Android Auto media channel. Browser microphone audio is accepted only for an authenticated, active session and is converted to the format required by the Android Auto microphone channel.

Audio and video use separate browser data paths, so exact transport-level lip synchronization is not guaranteed.

## Background behavior

Projection runs in a foreground service. Leaving the NavOnWeb activity detaches only the local preview when the decoder/WebRTC Surface remains valid, allowing browser output to continue. Returning to the app reattaches the preview.

Android or device-vendor power management can still stop the service. Force-stopping the application prevents automatic restoration until the user opens NavOnWeb again.

## Current limitations

- The user must enable and start Android Auto's Developer Head Unit Server.
- The supported projection endpoint is the same phone; arbitrary remote Android Auto endpoints are not exposed by the application.
- Direct browser use is intended for a trusted local network. Connectivity across NAT or unrelated networks is not guaranteed.
- Available codecs and sustainable resolution depend on the phone's hardware encoders and thermal limits.
- USB AOA transport components are present in the source, but the current endpoint resolver uses the same-phone loopback server.
- The optional JNI target is a compileable coordinate/viewport scaffold, not a linked native OpenAuto runtime.
